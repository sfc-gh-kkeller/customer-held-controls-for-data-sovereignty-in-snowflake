# Performance results

All numbers are client wall time in this repo's demo setup: X-Small warehouse `SOV_WH`, AWS eu-central-1, laptop as the on-prem side (Docker lake). The same workload where it applies: **average salary per department over the 200 demo employees**. p50/p95 over repeated runs; *first* is the first run of a series (warm warehouse unless noted). The result cache is off everywhere. Generated by `bench/run_all.py` – raw JSON in `bench/results/`.

## One-off steps

| Step | Time |
| --- | --- |
| Option 1: tunnel up → first answer (SPCS service already running) | 14.2 s |
| Option 2: TOTP step-up grant (portal call) | 330 ms |
| Option 2c: device start / approve (scripted) / redeem | 2.1 s / 319 ms / 2.8 s |
| Option 4: connect (ADBC, PAT) | 1.2 s |

## Findings

- **Option 2's call-back dominated its latency.** The broker checks that the query is RUNNING with `QUERY_HISTORY_BY_USER(RESULT_LIMIT => 1000)`. For a busy user that took 8–10 s on the server, every query. Adding `END_TIME_RANGE_START` (10 minutes) returns the same RUNNING row in about 0.3 s. The fix is in `opt2-keybroker/lambda/broker/handler.py`. The remaining ~3.3 s (a denied query takes as long) is the external function round trip through API Gateway and Lambda.
  Before the fix: aggregate p50 14.6 s; after: 4.1 s.
- **Option 1 fails closed, but quietly.** With the tunnel down, `QUERY_ONPREM` returns the agent's connection error as a value and `EMPLOYEES_SENSITIVE_LIVE` returns **0 rows** – no data, but also no SQL error. Measured: `no data, function returned the error as a value: "IO Error: Could not connect to…`, view rows after down: 0.
- **Option 1b is fastest on the data path** (DuckDB in the notebook container), but a headless run pays the notebook pool start and package install.
- **Option 2b's cost is the Python UDF**, not the key fetch: the probe without external access is already ~1.6 s; external access and the one fetch per query add ~0.7 s. The per-process memo did not survive between queries here (one fetch every query).
- **Options 3 and 4 are fast because the work is local**: Option 4 decrypts 1,000 cells in a few ms; Option 3 spends most of its time writing the aggregates back with `write_pandas`.
- **Homomorphic sums cost ~2–3 s** for 100 rows on an X-Small warehouse; the packed (SIMD) form is roughly 2× faster. Decryption on the client takes milliseconds.

Numbers are from a single demo account and laptop, with a few repetitions each. They show orders of magnitude and where time goes, not a sizing guide.
